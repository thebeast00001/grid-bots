# Routines Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Any bot can be given standing jobs in plain words ("every weekday at 8am, give me a briefing"). At each time the bot does the job on its own — model, tools, recent chat — and posts the result into its chat, with a notification. Each routine shows its next run, can be run now, paused, edited or deleted, and keeps a history of runs.

**Architecture:** `routines` + `routine_runs` tables and a repo; the reminders scheduler wakes for whichever is due first (reminder or routine); a runner claims due routines atomically and runs each one in the background through the same pipeline as chat (instructions, memories, tools, trimmed history) with a hidden `[[routine]]` prompt, saving the reply as an assistant message that starts with a `data-routine` part. Runs publish `run` events so the open chat shows the bot working. Bots get routine tools; the profile gets a Routines section with presets.

**Tech Stack:** as feature 1 (Next 16, PGlite/Drizzle, AI SDK 7 streamText + toUIMessageStream, chrono/luxon via lib/reminders/when.ts, Motion, Playwright, Vitest).

**Spec:** `docs/superpowers/specs/2026-11-19-next-50-features-design.md` → feature 2.

## Global Constraints

- Quality bar from the spec (tests first; desktop + phone, light + dark, reduced motion, worst-case data; security review; commit and push).
- Schedules use the reminders vocabulary: `repeat ∈ none | daily | weekdays | weekly | monthly | yearly` from `parseRepeat`, first time from `parseWhen`, next times from `nextOccurrence` (anchored, DST-safe). `none` = a one-time job that becomes `done` after it runs.
- Name 1–60 characters; instruction 1–2,000; at most 50 routines per bot.
- A run gets the bot's normal instructions and tools (remember, reminders, routines) minus `react`, the last 20 messages of its chat, and this prompt (never stored): `[[routine]] It's time for your routine "<name>" (<schedule label>). The user set it up to run on its own and isn't here right now. Do this: <instruction>\nReply with just the result, written for the user to read later.`
- A run is abandoned after **3 minutes** (`failed`, "Took too long").
- Missed while Grid was off: if the run time passed less than **12 hours** ago, run once now (late); otherwise record a `missed` run and move to the next time.
- One run per routine at a time; Run now during a run → 409.
- Failures are visible: the chat gets a routine message saying it couldn't run and why (e.g. "Connect a model"), the run is `failed` with the error.
- Presets in the profile: **Morning briefing** (weekdays 8:00 AM), **Evening check-in** (every day 9:00 PM), **Weekly review** (Sundays 6:00 PM).

## Review Focus

1. **Two scheduler wake-ups at the same moment** → each due routine runs once (atomic claim). (Task 1 test `claims each due routine once`.)
2. **Grid was off for days** → a routine due long ago is recorded as missed, not run with stale context; one due an hour ago runs late. (Task 1 tests.)
3. **No model connected / provider down** → the run fails with a message in chat and a failed history entry; the scheduler keeps going. (Task 2 test `a run without a model fails visibly`.)
4. **Run now pressed twice** → the second gets 409 while the first runs. (Task 3 test.)
5. **Bot deleted while a run is in flight** → nothing crashes; routines and runs go with the bot. (Task 2 test.)

**Files:** schema + `lib/db/migrations/0002_routines.sql` (drizzle-kit), `lib/routines/repo.ts`, `lib/routines/repo.test.ts`, `lib/scheduler.ts` (+ test in `lib/routines/schedule.test.ts`), `lib/client-types.ts`, `app/api/test/reset/route.ts`

**Interfaces (produced):**
- tables `routines` (`id` `rtn_`+12 hex, `bot_id` → bots cascade, `name`, `instruction`, `anchor_at`, `next_run_at` null when done, `repeat`, `status` `'active'|'paused'|'done'`, `last_run_at`, `created_at`) and `routine_runs` (`id` `run_`+12 hex, `routine_id` → routines cascade, `bot_id`, `trigger` `'schedule'|'manual'`, `status` `'running'|'done'|'failed'|'missed'`, `started_at`, `finished_at`, `message_id`, `error`, `late`)
- `RoutineView = { id; botId; name; instruction; repeat; status; nextRunAt: string|null; lastRunAt: string|null; scheduleLabel: string; running: boolean }`, `RunView = { id; routineId; trigger; status; startedAt; finishedAt; messageId; error; late }`
- repo: `createRoutine({ botId, name, instruction, at, repeat })`, `listRoutines(botId)`, `getRoutine(id)`, `updateRoutine(id, { name?, instruction?, at?, repeat? })`, `setPaused(id, paused)`, `deleteRoutine(id)`, `listRuns(routineId, limit=10)`, `claimDueRoutines(now): Promise<{ routine, late }[]>` (one UPDATE moving `next_run_at` on, or to null/`done` for one-offs; missed ones get a `missed` run and are not returned), `nextRoutineAt()`; every change publishes `{ type: "routines", botId }`
- scheduler: wakes at `min(nextDueAt(), nextRoutineAt())`, calls `deliverDue` then `startDueRoutines` (Task 2 provides it; Task 1 calls a no-op hook `onDueRoutines`)
